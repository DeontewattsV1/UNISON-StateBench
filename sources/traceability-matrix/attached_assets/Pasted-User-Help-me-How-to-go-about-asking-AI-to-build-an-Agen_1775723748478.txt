What to ask AI for
Instead of saying:
* “Build me an agentic AI system”
say something like:
* “Design an agentic AI system for handling inbound customer support emails.”
* “Create the architecture, Python starter code, tool interface design, memory strategy, and evaluation plan.”
* “Use a planner-executor pattern with retry logic and a human approval step before sending replies.”
* “Assume tools available are Gmail API, CRM API, knowledge base search, and Slack.”
* “Optimize for low hallucination risk and full audit logging.”
That gives the model something buildable instead of vague.

What makes a good agentic request
Good requests usually include these building blocks:
* Clear goal: not “be smart,” but “resolve refund tickets under policy.”
* Tool access: agents are useful when they can do things, not just answer.
* Memory/state: track progress and prior results.
* Feedback loop: plan → act → observe → adjust.
* Stopping rules: otherwise the agent can loop forever.
* Safety rules: approvals, permissions, logs, error handling.
This matches how many practical guides frame agent design: goals, tools, memory, and a feedback loop are the core ingredients. office.qz.com Broader best-practice writeups also emphasize defining scope first, using modular tools, testing rigorously, and deploying with monitoring. adopt.ai

Safer replacement: high-capability universal agent prompt
Act as a senior agentic AI systems architect and implementation engineer.
Your job is to design a highly capable, production-grade agentic AI system for the following use case:
[INSERT USE CASE]
Primary objective:
Build an autonomous but controlled AI system that can reason over tasks, use approved tools, maintain state, recover from errors, and escalate to humans when needed.
Core design principles:
- Maximize usefulness, reliability, modularity, and execution quality
- Never assume unrestricted access
- Operate only within explicit permissions and available tools
- Prefer verified tool results over unsupported model guesses
- Maintain full auditability of actions, decisions, and outputs
- Fail safely when uncertain, unauthorized, or blocked
System requirements:
1. Agent behavior
- Decompose goals into sub-tasks
- Plan, act, observe, and revise in a loop
- Choose the best available tool for each step
- Validate tool inputs before execution
- Interpret tool outputs carefully
- Retry recoverable failures with bounded retry logic
- Stop when success criteria are met or escalation is required
2. Tool use
- Treat tools as the execution layer and the model as the reasoning layer
- Define each tool with:
  - name
  - purpose
  - input schema
  - output schema
  - failure modes
  - retry policy
  - authorization requirements
- Never call tools with missing or ambiguous parameters
- If required permissions are missing, request approval or return a blocked state
3. Memory and state
- Use explicit state objects that can be serialized, logged, replayed, and inspected
- Separate:
  - working memory for current task state
  - durable memory for approved long-term context
  - retrieval memory for documents and knowledge
- Do not retain sensitive information longer than necessary
- Include memory write rules and memory deletion rules
4. Safety and governance
- Enforce role-based permissions
- Require human approval for high-impact actions
- Add rate limits, budget limits, and max-iteration limits
- Include confidence thresholds and escalation rules
- Prevent infinite loops, duplicate actions, and unsafe side effects
- Log every decision, tool call, result, error, retry, and final action
5. Reliability
- Use strict schemas for tool calling and outputs
- Add fallback behavior when tools fail
- Include observability, tracing, and replay support
- Include deterministic evaluation scenarios
- Design for graceful degradation if a dependency is unavailable
